# GLM-5.3-Flash W4 G64 部署

入口为公开 `ModelRecipe`：`glm-5.3-flash`；workflow 配置为
[`glm5_3_flash_autoround_w4g64.yaml`](../../../../configs_merak/workflows/xh2a/llm_models/glm5_3_flash/glm5_3_flash_autoround_w4g64.yaml)。
输入完整的 `weights/GLM-5.3-Flash`，包括语言、图像和视频处理资源。
产物校验遵循当前统一 Manifest 契约：交付文件校验和必须匹配，
运行时可新增缓存文件；不依赖旧版的 initializer digest cache 禁用扩展。

| 部分 | 部署精度 | 权重处理 |
| --- | --- | --- |
| 42 层非共享专家，288 专家/层 | W4 G64 A16 | AutoRound，保留 packed 整数载荷 |
| 普通 attention、dense MLP、共享专家 | W8 A16 | AutoRound W8 G64 |
| vision、head、router、indexer、mHC、卷积、DSA K/V 因子 | W8 A16 | xhquant RTN |
| KDA forget gate 两层 a 投影及 beta b 投影 | W16 A16 | 不量化权重 |

DSA 不预先对权重做吸收乘积。浮点 `kv_b_proj` 拆分、转置后量化 K/V 因子，
query 与 K 因子的运算仍在图内，避免对已经量化的投影再次量化。
两个常量 RHS MatMul 显式配置为 W8 A16；激活之间的 attention MatMul 保持 A16。
MatMul 的右侧通过 `act_schema_2.man_bit=8` 设置；普通 `w8a16` 的 weight schema 不控制这一路输入。
AutoRound 按原生 decoder block 优化，保留实际路由和 clamped SwiGLU。
量化算法是 AutoRound，保存为 GPTQModel 可读取的 packed 格式；配置中的
`quant_method=gptq` 描述该存储格式，`provider=auto-round` 和 recipe 记录实际算法。

## 完整模型分阶段执行

完整模型建议先用公开 workflow 生成独立 checkpoint，再用公开 build 导出；
这样导出失败也不会清理已经完成的量化权重。使用下方相同的 conda 环境和 GPU 设置：

```python
from pathlib import Path
from xhmodel_merak.workflows import AutoWorkflow
from xhmodel_merak.model_build import build_model
from xhmodel_merak.model_catalog import get_recipe

source = str(Path("weights/GLM-5.3-Flash").resolve())
workflow = AutoWorkflow.from_config(
    model_dir=source,
    config_path=get_recipe("glm-5.3-flash").default_variant.workflow_config,
)
quant = workflow.quant(output_dir="work_dirs/glm53-quant", device="cuda:0")
result = build_model(
    model_id="glm-5.3-flash", model_dir=source,
    quant_checkpoint=quant.quanted_model_dir,
    output_dir="work_dirs/glm53-w4g64", device="cuda:0", low_memory=True,
)
```

使用 YAML 中的正式参数：128 条 × 2048 tokens、200 次迭代、batch 1、梯度累积 2。
GLM53 只注册 `low_memory` 导出模式，显式关闭时提前报错；公开 build 自动合并
prefill/decode 的相同权重，不需要事后转换脚本。

## 一次完成量化和构建

在 ModelZoo 仓库根运行。默认单卡，GPU 编号按实际分配填写，映射为 `cuda:0`。

```bash
conda activate xhquant_55_tf_latest_20260828
export CUDA_VISIBLE_DEVICES=1
export PYTHONPATH="$PWD${PYTHONPATH:+:$PYTHONPATH}"
export OPENBLAS_NUM_THREADS=1
export TORCHINDUCTOR_COMPILE_THREADS=1
export CUBLAS_WORKSPACE_CONFIG=:4096:8
python -m examples_merak.unified_api.build \
  --model-id glm-5.3-flash --model-dir weights/GLM-5.3-Flash \
  --output-dir work_dirs/glm53-w4g64 --device cuda:0
```

默认 context 4096、prefill 256、decode 1、batch 1，视觉每帧容量 1024 patches。
AutoRound 默认 200 次优化、batch size 1、梯度累积 2、`nblocks=1`。
相较累积 8，每个 block 的训练前后向次数从 1600 降到 400；有效 batch 从 8 变为 2，
最终质量仍需验证。校准、加载、打包和导出的开销不按相同比例下降，总耗时以实际测量为准。
128 条 2048-token 样本、累积 2 的真实 5 层单卡短测已完成优化、保存及独立进程重载：
A100 80GB 上 CUDA 分配峰值约 72.0 GiB，保留峰值约 78.4 GiB。
该探针只运行 2 次迭代，用于验证资源与保存流程；完整 200 次迭代的质量验收另行执行。
校准按 seed 42 打乱随仓 pile JSONL，选取 128 条完整的 2048-token 样本，过滤过短和重复样本；
实际样本数、token 数、seed 和 tokenized SHA-256 写入 recipe 记录。损失非有限立即失败。
quant adapter 对未知参数报错。公开 build 完成校验后才发布最终目录，失败不留下可加载的半成品。

量化准备按 shard 流式解码原始 FP8，并保留原生 FP32 参数。本次 BF16 中间权重约 628 GB（585 GiB），
AutoRound 的初始 HF 加载仍需要容纳浮点模型的主机 RAM，随后逐 block 优化、即时打包保存，
启用 CPU/GPU 低内存选项；专家原权重保留在 CPU，按投影搬入 GPU，量化中间量在反向时重算。
这会增加传输和计算开销。单卡优化的显存与 batch size 和序列长度有关；降低 batch size 时
可增加 `quant.runtime.gradient_accumulate_steps` 保持有效 batch size。
导出始终使用低内存路径：视觉逐组件导出，
单卡配置用一个 FFN worker 逐层加载，其余权重由主图持有。
有多卡时可通过 `export.model.placeholder_export_workers` 增加并发；没有全模型一次导出的模式。
没有指定 `quant_output_dir` 时，公开 build 在成功后删除其自建量化工作目录，部署包不依赖它。

要保留 packed checkpoint 供重复导出，可使用 Python API：

```python
from xhmodel_merak.model_build import build_model
result = build_model(
    model_id="glm-5.3-flash", model_dir="weights/GLM-5.3-Flash",
    output_dir="work_dirs/glm53-w4g64", quant_output_dir="work_dirs/glm53-quant",
    device="cuda:0",
)
print(result.quant_artifact)  # work_dirs/glm53-quant/checkpoint
```

也可先调用 GPTQModel 的公开
`gptqmodel.recipes.glm5_3_flash_autoround.quantize_glm5_3_flash_autoround`，再复用其输出：

```bash
python -m examples_merak.unified_api.build \
  --model-id glm-5.3-flash --model-dir weights/GLM-5.3-Flash \
  --quant-checkpoint /path/to/glm53-autoround-w4g64 \
  --output-dir work_dirs/glm53-w4g64 --device cuda:0
```

重用时校验模型配置、完整张量清单、精度和来源一致性。量化输出禁止覆盖源目录。
原始 checkpoint 的 MTP 元数据保留，但额外预测层不加入 45 层部署主干。

## 文本、图片、视频 demo

首次执行会编译 W4 CUDA 扩展。共享机器可为任务指定独立缓存，避免等待其他任务的编译锁：

```bash
export TORCH_EXTENSIONS_DIR="$PWD/work_dirs/glm53-cuda-extensions"
export TORCH_CUDA_ARCH_LIST=8.0  # 本次 A100 验证配置
export MAX_JOBS=2
GLM_ARTIFACT_DIR="$(realpath work_dirs/glm53-w4g64)"
python -m examples_merak.unified_api.generate \
  --artifact-dir "$GLM_ARTIFACT_DIR" --device cuda \
  --prompt '请用一句话介绍你自己。' --max-new-tokens 32
python -m examples_merak.unified_api.generate \
  --artifact-dir "$GLM_ARTIFACT_DIR" --device cuda \
  --image /path/to/image.jpg --prompt '描述图片中的内容。' --max-new-tokens 64
python -m examples_merak.unified_api.generate \
  --artifact-dir "$GLM_ARTIFACT_DIR" --device cuda \
  --video /path/to/video.mp4 --prompt '概括视频中的变化。' --max-new-tokens 64
```

`--device cuda` 使用全部可见卡；`cuda:0` 表示单卡。入口自动启用 HMONNX V2 和 packed W4。
产物入口使用 `build_model` 返回的实际 `output_dir`；若工作目录经由符号链接访问，先解析实际路径。
多张图片/多个视频可使用 `examples_merak/llm/glm5_3_flash/generate.py` 的重复
`--image` / `--video` 参数，`--json` 同时输出 token ID 和耗时。

Host 使用原生 processor 完成 resize、patchify、视频采帧和时间戳，再回填视觉特征。
图使用固定容量；输入支持容量内的不同长宽比和视频帧数，真实 token 通过有效性 mask 处理。
默认单图预算和单视频总预算均为 256 个合并 token，每帧仍必须不超过 1024 patches；
文本和视觉占位 token 的总长度加生成长度不得超过 context。超容量报错，不静默截断。
当前支持 batch 1 贪心生成，缓存请求间重置；PageAttention、beam search、投机解码未接入。

## 产物与验收

交付整个 build 输出目录：`model_build_manifest.json`、`effective_workflow.yaml`、
`golden_meta_info.json`、`merak_config.json`、`hf_config/`、embedding、prefill/decode
及 vision 的 ONNX 和 external data。路径在包内相对引用，可搬移后运行。
图像和视频复用 26 个视觉组件，语言图各包含 42 个 W4 G64 `MoeBlock`、102 个浮点 gate Linear、
22 个 W8 常量 MatMul 和 34 个 W8 KDA 卷积。
构建执行实际图精度审计，结果进入 manifest 的 artifact metadata。
AutoRound checkpoint 使用 packed W4。当前 HMONNX 外部张量用 INT8 承载有符号 W4 码值，
加载时由 SDK 打包为 W4，因此部署包的磁盘大小不能按 W8 的一半估算。

当前 CI `test_glm53_gptq.py` 使用保留 G64、KDA、DSA、mHC、clamped MoE 和视觉的
最小原生合成模型，检查 packed 数据不变、公开 build、搬移/删除源目录后重载、
多模态重复生成、prefill 数值、常量 MatMul 精度退化及非法组件路径。
AutoRound 的真实优化、即时保存和独立进程重载回归在生产仓库执行。
数值对比固定生成前缀，保留每一步原始 logits 的误差和 top-1 一致性。AutoRound checkpoint
中的 router、indexer 等仍是浮点，导出时的 W8 量化可能改变接近的专家或选池排序；
这类离散变化需要定位，不能只用整体平均值掩盖，也不能在验收时固定路由来代替实际执行。
AutoRound 的本次执行记录另存 `work_dirs/glm53_autoround_w4g64_validation_20260912/`；
真实前 5 层单张 A100 80GB 探针使用 16 条 2048-token 样本、2 次迭代、batch 1、累积 8，
完成优化、保存、审计和独立进程重载；CUDA 分配峰值 72.0 GiB，保留峰值 78.4 GiB。
小模型还通过真实 AutoRound 加公开 ModelRecipe 的同进程构建。这些证据验证功能及资源，
只有实际完成的记录才构成整模验收证据。验证目标是 XH2a HMONNX 的 CUDA 模拟执行。
此前 `work_dirs/glm53_w4g64_validation_20260912/large_moe_address_check.json` 记录独立的真实尺寸地址验证：A100 CUDA、
288 专家、hidden 4096、intermediate 2048、top-8、W4 G64 A16，M=1/256 均访问
255～287 等高编号专家，与抽取同一批专家后重编号的结果逐位一致。该验证只覆盖
专家库寻址和对应运行路径，不替代整模量化质量和生成验收。

## Prefill / decode 共享权重

公开构建入口将两个图保存为 `language/prefill.onnx`、`language/decode.onnx`，
共同引用同目录的 `weights.bin`。只有 dtype、shape、字节长度和 SHA256 都相同的
外部张量才共享 offset，阶段专属常量分别保留。图校验和与产物 Manifest 同步更新，
整包可搬移，不依赖软链接。转换按块读写，不重新量化，也不改变算子精度。

此步骤减少最终产物的磁盘占用；分层导出阶段的临时文件仍计入磁盘峰值，
不能把最终权重减少一半等同于导出峰值减少一半。
